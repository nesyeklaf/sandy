# Field latency

The Field Latency plugin measures in every open sandy browser tab and stores the samples on the server.

- `sandy field-latency report [--since 24h] [--kind open|switch|slow|scroll] [--device <id|label>] [--merged] [--by-release [--by-device]] [--json]` gives, per device, percentiles per interaction (slowest p75 first), a scroll table and the device's hardware line. With more than one device it starts with an overview table (id, label, samples, idle/busy/unknown load counts, benchmark, cores). `--device` takes an id prefix (`a1b2c3`, `#a1b2c3`), part of the label (`firefox`, `windows firefox`) or `unknown`; `--merged` prints the old single table over all devices. Switch rows carry two numbers: p50/p75/p95/max until the thread is ready (readyMs), and "content p50"/"content p75" until the thread content is done (contentDoneMs, only samples that settled).
- `sandy field-latency report --by-release [--since 30d]` (also with `--device`; `--by-device` prints one such table and comparison per device) groups by sandy release: first seen, release key, n, p75 of switch first, switch first content, switch revisit, switch revisit content and open, and p25 of scroll smoothness, then compares the two most recently first-seen releases with deltas. Releases without a version or script hash (samples from before 0.3.0) show as `unknown` and are left out of the comparison. Use a long `--since` (30d), a release only shows up when it has samples in the window.
- `sandy field-latency recent [--limit 20] [--json]` lists the latest samples; switches show `content <ms>` (or `capped`, `aborted`) after the ready time.
- `sandy field-latency clear --yes` deletes every sample, for example before measuring a new deployment.

## Devices and load

- Each browser profile makes a random deviceId once (localStorage key `sandy-field-latency:device`, kept in memory when storage is blocked) and sends it with every record; the server stores it per sample row. Two machines with the same user agent therefore stay apart, and one machine with a Firefox update stays one device (the label is built from the latest user agent at report time, for example `Linux Firefox 158`, `Android WebView 156 (SM-S936B)`; the id is shown as its first 6 characters). Rows from before 0.3.3 have no id and report as `unknown device`; they are in the totals and in `--device unknown`, not in other `--device` filters.
- The hardware line per device comes from the newest record: benchmark (iterations per second), cores, memory (GB, Chromium only), screen size x devicePixelRatio, refresh rate (from refreshMs of the scroll calibration), platform and GPU (WebGL `WEBGL_debug_renderer_info` unmasked renderer, else the generic renderer; read once lazily, Firefox may mask it).
- Every sample may carry `load`: how busy the browser was in the 5 s before the interaction (pointerdown), so the sample's own work is not counted. busyPct is the share of that window by which a timer fired late (the timer is armed every 100-300 ms at random so periodic work cannot hide between ticks; lateness beyond a 4 ms jitter floor; sampling stops while the tab is hidden and the hidden gap never counts as lag; null when the sampler covered less than half of the window, for example right after load). maxLagMs is the largest single lateness. `pressure` (nominal/fair/serious/critical, from the Compute Pressure API, Chromium with a secure context and permissions policy only), `charging` and `batteryPct` (Battery API, Chromium) are null where the browser has no such API. The tab is always visible in a sample (hidden clicks produce none). Tab count and "agent is streaming" are not recorded: no cheap, reliable signal exists for them.
- Load bucket per sample: `idle` when busyPct is under 10 and pressure is not serious or critical, `busy` otherwise, `unknown` without load (older samples, lab browsers). The report columns "idle p75" and "busy p75" are the p75 of the first-ready time (ms) of each bucket with n in brackets; compare the slow device in idle first, then read busy as "what contention costs". busyPct is an ordinal signal, not CPU %: in headless Chromium and Firefox against a quiet page it read 0-0.2 %, and work blocking the main thread about 70 % of the time in periods of 120 ms to 1 s read 10.6-65 % (short periods read lowest, a single 2.5 s block read 47-48 %). The 10 % threshold sits between those, close to the weakest case; idle noise on real field devices (streaming threads, background load) is not measured, so revisit the threshold when a device sits above it with nothing running.
- The probe costs one timer about every 200 ms while the tab is visible (a few microseconds of main-thread work each), none while it is hidden, and is off in automated browsers.
- If the server is the previous version (rejects the new client or load keys), the client resends the batch without them and keeps that shape for the session: those samples have no device and no load until the page reloads against the new server.

## Lab browsers

- Headless or webdriver-driven browsers (the sandy lab under `scripts/perf`) are not field data: the collector runs there, but sends nothing and skips the device benchmark, the server drops records whose user agent contains `HeadlessChrome`, and the report leaves out such rows stored before 0.3.1.

## What a sample means

- open: from pointerdown on a button to the first painted frame that shows a new menu, listbox, dialog or popover (readyMs). mountMs is when its DOM appeared, settledMs when its opening animation finished.
- switch: from pointerdown on a thread link to the painted frame in which the URL, at least one timeline row of that thread and the composer are present (the same ready condition as scripts/perf in sandy). visit is first or revisit within this page load. A switch that is not ready after 15 s counts as a timeout. Its readyMs never changed meaning, so older field data stays comparable.
- switch content done (contentDoneMs, contentDone): from the same pointerdown to the last painted DOM change (added or removed nodes, text, and changes to style, class, hidden, aria-hidden, aria-expanded, open, data-state and the compact-composer fold attributes; no layout reads) inside the main content (`[data-sidebar="inset"]`: timeline, composer, plugin cards such as genui and the compact composer), once the switch is ready, no change is waiting for its paint, and the content stayed quiet for 1 s. A click on another thread before the first switch is ready ends the first content measurement as aborted. Sidebar and everything outside the inset (including the sidebar delegate) is ignored, as are changes to detached nodes. Because it is the paint of the last change, not the end of the quiet window, it is never below readyMs. contentDone is `settled` (value is real), `capped` (content was still changing 5 s after pointerdown; contentDoneMs is the last paint inside the cap, a lower bound, or null when the thread was not ready by then) or `aborted` (another thread switch started, the tab was hidden, or the switch timed out; no value). Only settled samples enter the content percentiles; the n column of the report shows how many were capped or aborted. A thread that streams output keeps changing and shows up as capped. Samples stored before 0.3.2 have no content mark and show `-` in the content columns. The 1 s window and the 5 s cap come from the render-attribution lab: gaps between content writes of one switch were p95 166 ms but reached 830-960 ms in a first visit with host writes at about 2 s, and bare content-done medians were 0.27-2.0 s.
- switch last content writer (contentSource, contentWrites; since 0.3.4, only on switch samples with a content mark): after the ready paint and before the content measurement closes, contentWrites counts the content changes (one per batch of DOM changes) and contentSource names who made the last one: the `data-sandy-plugin` id of the nearest plugin root around the changed node (for example `genui`), or `host` when no plugin root encloses it. Both are null on other samples and on switches stored before 0.3.4. The report shows per device a "Switch last content writer" table (`byDevice[].writers[]` in `--json`: writer, n, sharePct, contentN, contentP50): writer is the contentSource, `none` when nothing changed after the ready paint (contentWrites 0, the content was done at ready) and `unknown` for rows stored before 0.3.4; share is of that device's switch samples; content p50 uses settled samples only, as the content columns do. Read the gap between painted and really done from it: a writer with a high share and a high content p50 (or mostly capped) is what keeps the thread changing after the ready paint. A host writer that keeps ticking until the 5 s cap points at a host-side timer or stream, a plugin writer at that plugin's card.
- slow: any other interaction whose Event Timing duration reached 100 ms, labeled with the event name and its target.
- eventMs, inputDelayMs, processingMs, presentationMs come from the Event Timing API (Chromium; Firefox gives event durations only). frameMs, blockingMs, styleLayoutMs and scripts come from Long Animation Frames (Chromium only) during the interaction.

- tracedMs and phases come from sandy's own trace spans (`performance.measure` entries named `sandy:switch`, `sandy:open` and `sandy:<kind>:<phase>`), on hosts that ship them. A switch splits into input (click until the route changed), render (until the thread screen committed), timeline (until its rows were there) and paint; an open into render and paint. phases in the report are medians per phase, so they need not add up to traced p50. Keyboard and link switches and keyboard-opened overlays, which have no pointerdown, appear only through these spans, labeled "keyboard or link switch" and "keyboard <overlay>".
- The client record carries deviceMemoryGb and effectiveType next to cores and viewport, to tell an old laptop from a fast desktop.

Clicks while the tab is hidden, clicks on the thread that is already open and clicks that open nothing produce no sample.

## Scroll smoothness (kind scroll)

- A scroll session is a user-initiated scroll: a `scroll` event (any container, captured on the document) that follows a wheel, touch, pointer-down or scroll-key event within 500 ms. Scrolling nobody asked for, such as a timeline following streamed output, starts no session. A session ends 300 ms after its last scroll event, when the tab is hidden (discarded), after 20 s or 4096 frames (truncated), and sessions under 12 frames are dropped.
- Only while a session runs, a requestAnimationFrame loop writes frame timestamps into one preallocated buffer. Outside sessions nothing runs, apart from one 60-frame calibration about 3 s after load (retried while the tab is hidden).
- refreshMs is the display refresh interval: the lower quartile of the rAF intervals in that idle calibration, lowered to the session's own lower quartile (which includes its idle tail) when that is more than 10 % smaller. 6.9 ms means 144 Hz.
- Per session: durationMs, frames (intervals), dropped (intervals longer than 1.5 x refreshMs), p95FrameMs, maxFrameMs, smoothnessPct = presented / expected frames = frames x refreshMs / duration, capped at 100. A 60 fps scroll on a 144 Hz display therefore scores about 41 %. The label is the scroll container: the name of its first `data-*` attribute that contains scroll, viewport or timeline (without `data-`), else its id, aria-label or role, else the tag name; `page` for the document.
- Long animation frames that overlap the session fill frameMs, blockingMs, styleLayoutMs and scripts, as for other samples.
- In the scroll table smooth% p25 is the level that 75 % of sessions reach or beat, so higher is better; the frame columns are ms, lower is better.

## Releases

- Every client record carries sandyVersion (the content of `<meta name="sandy-version">`, if sandy sets it) and appScript (the hash in the main module script `index-<hash>.js`). The release key is `<sandyVersion>+<appScript>`, or whichever exists, else `unknown`. The server stores it per sample, so first-seen dates cover all stored data, not only the report window.

## Server and network phases

- For sandy:switch and sandy:open traces, fetch and XHR requests to the same origin that started inside the span and finished by its end are matched with Resource Timing. Overlapping requests form one step; the request that finishes last gates it, and steps that follow each other add up (a waterfall).
- On the gating requests: server is the Server-Timing `total` duration (else the largest metric), never more than the wait; network is the wait (responseStart - requestStart) minus server. Without a Server-Timing header only network appears. Both go into phases next to input, render, timeline and paint, so they show in "phases p50".

## Device benchmark

- Once a day per browser (localStorage key `sandy-field-latency:benchmark`), about 5 s after load, when the tab is visible and idle, a dedicated worker from a Blob URL runs `sandyBenchmarkIndex` three times (about 300 ms each) and the client record stores the median as benchmarkIndex (iterations per second, higher is faster), next to cores (navigator.hardwareConcurrency). It is the same function that the lab's calibrate script runs.
- The report shows it in its header. `sandy field-latency report --json` returns an object: `{ since, device, devices, groups }` (with `--by-release`: `{ since, device, devices, releases, compare }`). Read the index at `.device.benchmarkIndex`; `.device` is the most recently seen device that has one, `.devices[]` has one entry per device id (rows without one: per user agent and core count) with id, label, n, cores, deviceMemoryGb, devicePixelRatio, screen, refreshMs, platform, gpu, userAgent and lastSeen. Since 0.3.3 the JSON also has `.byDevice[]` with `{ device, n, load, groups }`, and with `--by-release --by-device` a `byDevice[]` of `{ device, n, releases, compare }`. Samples and `recent --json` carry `load` and `device`. Before 0.3.0 the JSON was the bare `groups` array.
